# 提示词模板

这些模板来自《钢铁突围：前线行动》的真实迭代方法复盘，不是聊天记录的逐字导出。替换方括号内容后即可使用；已有项目应同时提供项目路径、截图或报错。

## 1. 从零开始做游戏

```text
我想制作一款[题材]的[2D/3D]游戏，核心玩法是[一句话描述核心循环]。

开发环境：
- 引擎：[Godot版本]
- 语言：[GDScript/C#]
- 目标平台：[Windows/Web/其他]
- 分辨率：[目标分辨率]

第一阶段必须完成：
1. [玩家移动、跳跃等]
2. [基础攻击或互动]
3. [一种敌人或挑战]
4. [一个可完成的任务]
5. [开始、失败和完成流程]

开发要求：
- 先检查当前工作区和已有文件，再按现有结构实现。
- 把需求拆成可运行的小阶段，每完成一阶段就启动验证。
- 不只给方案，直接创建或修改需要的文件。
- 出现报错时根据日志定位并修复，不要绕过错误。
- 保留与本次需求无关的已有内容。

美术要求：
- 画风：[像素军事/卡通/写实等]
- 角色在待机、移动、攻击和切换武器时必须是同一个人。
- 精灵使用透明背景，无白底、白边和多余文字。
- 所有动画帧统一尺寸、脚底基线和人物比例。

验收标准：
- 项目可以从主场景启动。
- 玩家能完成一次完整玩法循环。
- 没有解析错误、明显碰撞卡死、UI重叠或素材错位。
- 最后告诉我运行方法、完成内容和仍未覆盖的边界。
```

## 2. 增加一个玩法功能

```text
请在现有 Godot 项目中增加[功能名称]。

当前情况：[目前已有的系统和操作]
期望行为：[玩家如何触发、画面如何表现、结束后如何恢复]
关联模块：[角色/武器/敌人/任务/UI/存档]
限制条件：[不能修改的系统、必须复用的素材或数值]

请先定位现有状态和数据由哪个脚本负责，再做最小范围修改。完成后实际运行并验证：
1. 正常流程；
2. 边界情况；
3. 与原有功能的切换；
4. 失败或取消后的恢复。
```

## 3. 根据截图修 Bug

```text
请结合我提供的截图修改这个问题。

复现位置：[关卡和大致坐标]
复现操作：[按键或操作顺序]
当前表现：[截图中错误现象]
正确表现：[我希望看到的结果]
修改范围：[只修改什么，不要修改什么]

请检查对应场景节点、脚本状态、碰撞体、素材透明度和锚点，找到根因后再修改。修复后在相同位置复测，并检查相邻区域是否产生新问题。不要只隐藏画面问题，也不要顺带改变其他玩法。
```

## 4. 生成并接入角色或武器素材

```text
请为现有游戏生成并接入[角色动作/武器/敌人/载具]素材。

视觉基准：[现有角色或截图路径]
画风：[像素风、视角、年代、色彩]
主体要求：[身份、服装、轮廓、朝向、武器]
输出要求：[透明背景、完整主体、无文字、无白边]
动画要求：[动作列表、帧数、统一画布和脚底基线]

重要限制：
- 所有动作必须保持同一角色的脸、头盔、服装、体型和比例。
- 切换武器只能改变武器和必要的手臂姿势，不能换成另一个人物。
- 接入后检查透明通道、裁切、尺寸、锚点和Godot导入设置。
- 在待机、移动、射击和切换武器之间实机验证，不能只生成图片。
```

## 5. 限定范围的精确修改

```text
[对象A]在[状态1]和[状态2]下的大小不一致。请以[指定状态]的大小为基准，只统一显示比例和脚底位置。

不要修改角色素材、移动速度、碰撞体、武器数值、其他动画或关卡内容。完成后对比两个状态，并确认切换时没有缩放跳变和悬空。
```

## 6. 扩展关卡内容

```text
请扩展第[几]关，但保留现有关卡路线和已完成内容。

目标体验：[节奏、难度、时长]
新增内容：[敌人、地形、补给、事件、Boss]
任务顺序：[目标1 → 目标2 → 撤离]
平衡要求：[玩家血量、Boss血量、弹药供给]
美术要求：[背景层次、场景物件、整体画风]

请先画出简短的关卡流程，再分段实现。每段都验证玩家能够通过，避免死路、跳跃高度不足、碰撞卡死、敌人出生在视野外持续攻击以及装饰物悬空。
```

## 7. 回归检查

```text
刚才的修改出现了新问题：[问题列表]。

请不要重新设计整个系统。先比较修改前后的角色资源、动画区域、缩放、状态切换和输入逻辑，找出回归来源。修复后依次验证待机、移动、跳跃、射击、受击、换武器和死亡，确保所有状态仍是同一个角色并保持相同比例。
```

## 8. 打包和发布

```text
请把当前 Godot 游戏整理成可公开试玩的 Windows 版本。

发布名称：[游戏名称]
版本号：[例如 v0.1.0]
发布范围：[源码仓库/Windows压缩包/GitHub Release]

发布前完成：
1. 导入资源并运行自动化测试；
2. 检查主菜单、关卡加载、暂停、返回和存档；
3. 使用 Release 配置导出 Windows x64；
4. 确认 EXE 和 PCK 可以从独立目录启动；
5. 添加操作说明、版本边界、素材说明和校验值；
6. 检查 Git 中没有缓存、临时文件或隐私信息。

上传完成后返回仓库和 Release 链接，并说明玩家应该下载哪个文件。
```

## 推荐写法

一条容易执行的提示词通常包含六部分：

```text
目标 + 当前状态 + 证据 + 期望结果 + 修改边界 + 验收方法
```

与其说“这里不好看，改一下”，更推荐说明对象、位置、参考画风、不能改变的内容，以及怎样才算修好。
